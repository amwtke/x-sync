大脑与大模型的同步，始于你与代码的同步

整合目录中的八篇心得：在 Loop Engineering 与 Coding Agents 普及后，工程师对需求、代码仓库、技术栈和交付系统的理解是否仍然与真实系统同步；校正信息论类比，并提出可测量的人—仓同步剖面与 Agent 自主权边界。

Loop Engineering 时代，写代码更快以后，更要理解自己交付的系统

当代码生成越来越便宜，真正稀缺的可能不再是“把代码写出来”的能力，而是：你是否仍然理解自己正在交付的系统。

Loop Engineering 降低实现成本，却没有消除理解门槛

Loop Engineering 可以理解为把大模型放进一个能够读取代码、调用工具、修改文件、运行测试、观察结果并继续迭代的闭环。Agent、Skill、Harness、测试环境和反馈机制，都是这条闭环的一部分。它比一次性的 prompt 更接近真实的软件工程，也确实能显著提高交付速度。

但工具变好之后，一个容易被忽略的问题浮现出来了：好的 Agent Skill，是否足以让一个缺乏主动理解和验证习惯的工程师，稳定产出与优秀工程师同等水准的系统？

现有证据支持一个有限结论：AI 可以帮助经验较少的工程师更快完成局部任务，却不会自动让所有人同样擅长理解架构、选择技术和检查结果。已有大规模现场实验显示，经验较少的开发者同样可以从生成式 AI 中获得明显的短期生产率提升；因此，简单断言“普通工程师不可能追上”并不严谨。一项覆盖 4,867 名开发者的现场实验支持的是“AI 普遍有帮助”，而不是“AI 已经消除了能力差异”。

另一面的证据也值得警惕。Anthropic 对实际 Coding Agent 会话的观察发现，任务相关专业度越高，会话越可能成功；不过该研究基于会话分类器，并没有直接观察生产结果，只能算相关性证据。How Claude Code is used in practice 一项只有 52 名参与者的小型随机实验还发现，使用 AI 完成陌生库的开发任务后，参与者的即时掌握度低于手写组，差距尤其集中在调试；主动要求解释、用 AI 帮助理解的人则表现得更好。How AI assistance impacts the formation of coding skills

这几项结果放在一起，得出的不是“不要使用 AI”，而是一个更细的结论：

AI 能替你完成越来越多的实现动作，但“代码已经完成”和“你已经理解系统”仍然是两件不同的事。

从 Vibe Coding 的甜蜜期到失控期

Vibe Coding 在项目早期往往非常顺滑。代码库近乎空白，架构约束少，需求大部分还在人的脑中。此时，一条 prompt 可能同时定义需求、技术方案和代码形态；模型的常见模式也足以覆盖大多数问题。

随着项目增长，情况会发生变化：

  • 需求有了历史，今天的指令可能与三个月前的业务决定相冲突；
  • 代码有了隐含约束，一个看似多余的分支可能承担幂等、权限或兼容责任；
  • Redis、MySQL、Caffeine、Seata、Elasticsearch、Spark、Flink 等技术逐渐进入系统，每一种技术都带来自己的状态、边界、失败模式和运维要求；
  • 一个局部改动可能穿过缓存、事务、消息、索引和下游消费者；
  • 文档、代码、测试和线上行为甚至可能互相矛盾。

这时，人可能已经忘记需求的前因后果，也未必理解所有技术的运行机制。如果工程师对系统的理解本来就是错的，那么 prompt 写得越清楚，大模型反而可能越高效地执行错误决定。

可以把这种现象称为理解债务：代码和系统已经变了，人脑里的系统地图却没有跟着更新。它不像技术债那样一定能在代码里被搜索出来，最初只表现为无法解释某段逻辑、不能预测影响范围，或者不断发出彼此冲突的需求。当生成代码的速度超过人理解变化的速度，理解债务就会越积越多。

一个典型的错误方案，是让前端直接连接 Elasticsearch 做检索。在极少数经过专门安全设计的环境中，浏览器访问搜索服务并非逻辑上绝对不可能；但在多数生产架构里，这会绕过服务端鉴权和业务边界，暴露存储拓扑，并把客户端与索引结构直接绑在一起。这个例子真正暴露的不是“不会调用 ES”，而是不清楚请求应当怎样经过前端、服务层和数据系统，也没有意识到其中的安全边界。

因此，代码规模变大后觉得“模型越来越蠢”，可能包含三种不同现象：

  1. 模型确实没有取到完成当前任务所需的代码和证据；
  2. 人已经与需求或代码现状失去同步，向模型发出了矛盾或错误的指令；
  3. 人和模型都理解错了，却因为两边意见一致而误以为结果可靠。

第三种最危险：你和 AI 可以完全对齐，但共同对齐在一个错误认识上。

工程师、Agent 和代码必须对得上

一个工程任务里有三个角色：

  • System（代码与交付系统）：当前的需求、代码、配置、数据和线上运行方式；
  • Engineer（工程师）：理解需求、做技术判断并检查交付结果的人；
  • Agent（大模型）：根据 prompt、读到的代码和工具结果完成任务的执行者。

三方同步，不是要求工程师背下整个仓库，而是要求三方对当前任务的几个关键问题有一致认识：系统现在怎么运行、这次要改什么、哪些规则不能破坏，以及怎样证明改动真的正确。

三条边缺一不可：

哪两方要对上 要回答的白话问题 常见做法
工程师 ↔ 代码 工程师是否真的知道系统现在怎么跑？ 读代码、回看需求、跑 trace、询问模块负责人
Agent ↔ 代码 Agent 是否读过相关文件，并用测试确认过结果？ 搜索代码、调用工具、跑测试、看日志
工程师 ↔ Agent 任务有没有说清楚，做错时是否知道停下来？ 写清目标、非目标、验收标准和停止条件

这也解释了为什么“把整个仓库塞进上下文”不是根治方案。长上下文实验表明，模型能接收某个长度，不等于能稳定使用其中每条信息；相关内容的位置、语义关联和输入长度本身都可能影响表现。Lost in the Middle、NoLiMa 以及一项控制了检索质量的 EMNLP 2025 研究都从不同角度说明了这个问题。

真正需要做的不是一味增加 token，而是每一步都给 Agent 提供少量但相关、最新、能够通过测试或运行结果核对的事实。

信息论可以借，但必须知道借的是什么

“信息量、熵、信道、带宽、噪声、信息差”等概念很有解释力，但如果把它们当成严格的信息论结论，就会产生误导。

Shannon 1948 年的原始论文研究的是符号如何在给定信道中可靠传输，并且主动把语义问题放在通信工程问题之外。工程实践关心的却恰恰是语义：工程师和 Agent 是否理解了正确的业务含义、系统边界与因果关系。因此，更合适的做法是把信息论当成受约束的类比，而不是证明。

信息论当然深刻影响了机器学习：熵、交叉熵、KL 散度等概念已经用于训练和分析模型。可是，一个理论推动了 AI 的发展，并不意味着所有“人不理解代码”的问题都能被直接叫作 Shannon 熵。大模型根据概率预测后续 token，也不能单独证明“它无法推理”或“它不能成为 Agent”。更直接的工程问题是：模型一开始并不知道项目现在是什么样，生成的代码也不会自动保证正确。

术语 严格含义 在工程讨论中的安全用法
信息量 某件事发生得越意外，带来的信息越多 不要说“人有 101、项目有 100”，改说“当前任务需要哪些知识”
熵 对一组可能结果有多不确定 代码行数多不等于熵大，可以直接说“还不知道多少关键事实”
信道容量 一条信道最多能可靠传多少数据 Context Window 很长，不等于模型能稳定用好全部内容
噪声 信号在传输过程中受到的干扰 过期文档、矛盾需求可以直接叫“错误或冲突的上下文”
互信息 两组数据共享了多少统计信息 没有明确数据和计算方法，就不要声称测出了“人仓互信息”
反馈 把结果送回去，帮助下一步调整 测试和日志能帮助纠错，但不要把它说成自动扩大信道容量
信息势能 不是标准信息论概念 改说“知识差距”“理解偏差”更清楚

这里还有两个容易忽略的细节。第一，更多输入未必带来更多有效信息；无关或过期内容可能增加推理负担。第二，重复不一定是噪声；把权限、事务、兼容性这类关键规则用固定格式再写一遍，有时反而能帮助纠错。

为什么“率失真”最值得借用

率失真理论原本研究有损压缩：当我们不要求把原始信息一模一样地还原时，最少要用多少数据，才能把误差控制在可接受范围内？它包含三个关键部分：

  • Rate（码率）：平均要用多少 bit 表示一个来源符号。码率越低，通常意味着压缩得越狠；
  • Distortion（失真）：原始内容与还原内容之间的损失。它不是一个天然固定的数，必须先规定“哪一种错误有多严重”；
  • Rate–Distortion Function，R(D)：在平均失真不超过 D 的条件下，理论上至少需要多高的码率。允许的失真越大，所需的最低码率通常越低。

最重要的不是公式，而是必须先定义失真的代价。压缩一张普通照片时，少量像素偏差也许可以接受；压缩一张包含合同文字的扫描件时，让数字和文字变得不可辨认就不能接受。同样一种信息损失，在不同用途下可能有完全不同的后果。MIT 6.441 的率失真课程笔记给出了它的正式定义与推导。

工程师脑中的“系统地图”可以看作这种思想的一个类比：人不可能把整个仓库逐字记住，只能保留一份经过取舍的理解。关键不在于记住多少，而在于这次任务最不能记错什么。

例如，任务是“修复下单后 MySQL 与 Redis 数据不一致的问题”。这时，系统地图至少要保留：

  • MySQL 和 Redis 谁是最终可信的数据来源；
  • 数据库事务在哪里开始和提交；
  • 缓存是在提交前还是提交后删除或更新；
  • 并发请求、失败重试和幂等逻辑怎样处理；
  • 用什么测试、日志和监控判断修复是否生效。

与这次任务无关的后台页面颜色、报表排版或其他模块的类名，可以暂时不记。页面颜色与缓存一致性没有业务关系，它只是一个“当前任务可以安全忽略的细节”的例子。如果任务改成重做后台主题，页面颜色就会变成必须保留的信息；判断标准会随任务改变。

因此，本文真正借用率失真的不是一条可以直接计算“人仓同步值”的公式，而是三个思考动作：

  1. 承认人的系统理解一定是一份有损摘要，不追求背下整个仓库；
  2. 先按当前任务定义哪些错误代价最高，再决定哪些细节可以忽略；
  3. 把有限的注意力和 Agent 上下文优先留给高代价信息，例如安全边界、事务规则、数据所有权和失败恢复。

这个类比还有一个安全边界：率失真理论通常约束平均失真，但工程风险不能全部取平均。一次权限绕过、资金错账或不可恢复的数据破坏，不能被一百个回答正确的低风险细节抵消；这类规则必须作为不可突破的硬约束单独检查。

至于通过测试和日志发现遗漏、再修正理解，属于 Loop Engineering 的反馈过程，不是率失真理论本身。除非真的定义了信息来源、概率分布、编码方式和失真函数，否则这里始终只是受信息论启发的工程类比。

这更像控制问题：想改好系统，先得知道它怎么运作

信息论有助于理解传递与不确定性，而控制论更接近这一问题的核心。

Conant 与 Ashby 的“良好调节器定理”在特定数学前提下讨论了控制者与被控制系统之间的关系。原论文带来的工程启发可以转述为：

要可靠改变一个系统，操作者至少要准确理解与当前任务有关的那部分系统。

这不意味着人必须记住全部代码。Parnas 关于信息隐藏与模块化的经典工作说明，清楚的模块边界、接口和规则，可以把这次任务不需要知道的细节挡在外面。On the Criteria to Be Used in Decomposing Systems into Modules

好架构的一个核心价值，就是让工程师改一个局部功能时不必理解整个系统。

Peter Naur 在 1985 年提出“Programming as Theory Building”：编程的产物不只是代码，还包括程序员对“这个问题为什么要这样解决”的理解。原论文90032-8) 放到 AI 编程时代，这个判断变得更尖锐：

代码可以飞快增长，人对代码的理解却可能跟不上。

所以，优秀工程师的优势不一定是记得更多类名和语法，而是他们通常更善于：

  • 能把一个请求从入口到数据落库的完整路径讲清楚，而不只看局部代码；
  • 知道数据归谁管理，以及事务、安全和兼容性等哪些规则不能破坏；
  • 理解项目所用框架和基础设施的工作原理，知道一个改动应该放在哪一层，而不只是会复制注解与配置；
  • 预测修改会穿过哪些模块、协议与运行状态；
  • 察觉自己不知道什么，并知道到哪里寻找证据；
  • 把复杂问题拆成范围清楚、可以分别测试的小任务；
  • 设计失败信号、测试、灰度与回滚，而不把“代码生成成功”当成交付成功。

以 Spring Boot MVC 微服务为例，“熟悉技术栈”不只是会写 @RestController。工程师不必背下每一行框架源码，但至少应该能够解释一条请求的大致路径：

内嵌 Tomcat 接收并解析 HTTP 请求 → Servlet 容器完成映射并构造 FilterChain → Spring Security 检查请求 → DispatcherServlet 分发请求 → Controller 执行业务逻辑 → 结果写回响应

这条简图背后还有几个决定代码行为的细节。Servlet 容器的 FilterChain 通常包含 DelegatingFilterProxy，它把工作桥接给 Spring 管理的 FilterChainProxy；后者选择第一个匹配的 SecurityFilterChain，再按配置执行认证、授权、CSRF 等安全 Filter。任何一个 Filter 都可能直接返回 401 或 403，因此请求不一定能到达 Controller。只有安全检查通过后，请求才继续到 DispatcherServlet。Spring Security Servlet Architecture

DispatcherServlet 会向 HandlerMapping 询问该由谁处理，并取得相应的拦截器；随后由合适的 HandlerAdapter 调用这个处理者。在常见的注解式 MVC 中，具体实现会找到 @Controller 或 @RestController 方法；@RestController 的返回值通常再由 HttpMessageConverter 写成 JSON 等响应。Spring MVC DispatcherServlet、DispatcherServlet Processing

IoC、AOP 和自动配置则主要决定应用启动后“有哪些对象、它们怎样连接”，不是请求每经过一步就重新运行一次。IoC 容器负责创建 Bean、注入依赖并管理生命周期；事务、方法安全和缓存等声明式能力常通过代理实现；Spring Boot 的许多自动配置会在启动时根据 classpath、已有 Bean 和配置项装配默认实现，并在开发者提供相应 Bean 时让位。Spring Boot Auto-configuration

框架内部也不是一堆需要死记的设计模式名词，而是一组解决具体问题的办法：DispatcherServlet 是统一入口的前端控制器；HandlerMapping、HandlerAdapter 和异常处理器等是可替换的策略；共享处理骨架提供固定流程和可覆盖的钩子；BeanFactory 与 FactoryBean 处理不同层次的对象创建；应用事件提供发布—监听机制；AutoConfiguration.imports 和其他类似 SPI 的发现机制加载可选能力；“约定优于配置”则给常见场景默认值，同时允许覆盖。

这些知识会直接改变代码应该写在哪里。例如，401 没有进入 Controller，可能是安全 Filter 已经终止请求；在默认代理模式下，类内部自调用可能绕过 @Transactional 代理；自定义 Bean 可能让某项自动配置主动退出；REST 返回值通常由消息转换器处理，而不是必须经过视图解析。真正的技术栈理解，是能沿着请求链解释这些现象、定位证据并预测改动后果，而不是能背出所有 Filter 顺序或设计模式名称。

设计模式可以成为共享坐标，但不能只报模式名

自然语言很适合说明“为什么要做”和“用户应该看到什么”，却未必能稳定表达系统由哪些部分组成、数据怎样流动、扩展点在哪里。设计模式和架构模式的价值，是用一个共同名称快速说明这套基本结构，也就是系统大致“长什么样”。

例如，对 Agent 说“这是一个分阶段的 processor pipeline”，比只说“把这段复杂计算拆开”多传递了几项预期：计算由若干阶段组成，阶段遵守相似接口，数据按既定方向流动，新步骤应插在明确位置，每个阶段应当可以单独观察和测试。这个模式名像一张压缩过的地图，能让工程师、Agent 和代码更快找到共同坐标。

但模式名只是起点。同一个“责任链”，有人会理解成“多个候选处理者中有一个接手后结束”，有人会理解成“所有处理器依次执行”，还有人会想到可以在调用 next() 前后包裹逻辑的中间件。线性的逐步数据转换通常更接近 Pipes and Filters；出现分支、汇合、等待和补偿时，可能已经需要工作流、DAG 或状态机。只报一个模式名，反而可能造成“三方都以为已经对齐”的假象。

真正稳定的共享语言至少有三层：

层次 它解决什么问题 还缺什么
模式名 快速说明系统的基本形状和常见分工 没说明项目采用了哪一种变体
项目内契约 写清拓扑、输入输出、顺序、状态、失败和整体规则 文字可能过期，实现也可能绕开它
可执行约束 用类型、依赖检查、契约测试、端到端测试和运行指标固定规则 仍需人解释没有被形式化的业务含义

这也符合已有研究给出的警告：在一项针对 Code LLM 的设计模式实验中，不同模型表现出不同的模式偏好，也会出现没有遵守指定模式的情况。因此，模式词可以帮助表达意图，却不能替代对生成结果的检查。Do Code LLMs Understand Design Patterns?

以 MyLuncher 为例，下面这段 Java 接口用最小契约规定了所有阶段的共同外形：

public interface Processor<T extends ProcessorContext> {
    void process(T ctx) throws ProcessorException;
    int getPriority();
    String getProcessorName();
}

真正推进流水线的是 AbstractService.innerRun。下面节选排序、调用与短路的关键行，日志、异常和忽略规则等从略：

processors = processors.stream()
        .sorted(Comparator.comparing(Processor::getPriority))
        .collect(Collectors.toList());

for (P processor : filterProcessors(processors, processContext)) {
    processor.process(processContext);
    if (processContext.isFinished()) {
        break;
    }
}

查看中央执行循环源码

这段代码把约定变成了可以核对的事实：Processor 按优先级排序，中央循环依次调用它们，所有阶段接收同一个 Context，并且可以通过 finished 提前结束。阶段边界、插入位置和执行顺序，因此比一大段混合逻辑更容易被人和 Agent 看见。

准确地说，它更像责任链式的集中编排处理器流水线，而不是教科书式责任链：Processor 不持有下一个处理器，也不自行决定是否调用 next()，推进顺序由中央 Service 控制。这个区别并非咬文嚼字；如果 prompt 只写“增加一个责任链节点”，Agent 仍然不知道该节点是否必经、能否终止后续步骤、应该读取什么，以及异常由谁接管。

统一接口也只是为独立测试创造了边界，并不会让阶段天然独立。MyLuncher 的测试里，两个 Processor 通过 Context 形成了一个真实但隐含的顺序依赖：

// @SortOrder(1)：前一阶段写入共享 Context
ctx.getEvents().add(this.stringToAdd);

// @SortOrder(2)：后一阶段假定 events[0] 已经存在
String s = ctx.getEvents().get(0);

查看两个测试 Processor 的完整源码

这种依赖可以工作，却没有出现在方法类型里；如果不把 Context 字段的读写权、前置条件和后置条件写清楚，耦合只是从长函数里搬进了共享对象。

同样，pipeline 解决的是分解和理解问题，不会自动解决计算速度问题。MyLuncher 的 runProcessorsAsync 方法只是把同一个 innerRun 交给 Executor，内部 Processor 仍然顺序执行。计算密集型项目若要真正提高吞吐，通常还要对瓶颈阶段做批处理、数据并行或向量化，并明确并发度、队列上限、顺序与背压；有复杂依赖时则应把分支和汇合画成显式的执行图。

因此，工程师不必了解每个 Processor 内部算法的全部数学细节，但团队必须共同知道：阶段怎样排序，交换什么数据，谁能修改状态，什么时候终止，失败和重试怎样传播，以及整条流程最终必须守住什么业务规则。单个 Processor 的测试全部通过，也不能证明它们组合起来一定正确。

把这个想法用在 prompt 中，不是用一个模式名替代所有自然语言，而是把业务目标、架构形状和本地约束放在一起：

业务目标：这次要改变什么，明确不改变什么。
架构形状：顺序 Processor 流水线；每个选中阶段都执行，并非“一个处理后即停止”。
新增位置：放在 Normalize 与 Score 之间，不允许绕过权限与校验阶段。
阶段契约：输入、输出、前置条件、后置条件，以及允许读写的 Context 字段。
运行规则：顺序、并发、超时、重试、幂等、取消和资源上限。
整体规则：跨阶段仍必须成立的业务不变量。
验证证据：阶段测试、相邻阶段契约测试、端到端场景和运行指标。

这也引出了一个与“人仓同步程度”不同的概念：仓库的可同步性。前者描述某个人此刻对某个任务了解多少；后者描述仓库是否主动暴露自己的结构、业务语言和约束，让人和 Agent 能够低成本地重新跟上。稳定的模式、清楚的命名和模块边界、可查看的运行拓扑、架构测试与可观测性，都在提高可同步性。

设计模式不是答案，而是三方共享的坐标；只有当模式被项目内契约、代码结构、测试和运行规则固定下来时，它才真正帮助工程师、Agent 与代码保持同步。

对于已经能做出这些判断的工程师，缺少的往往只是一个写代码快、搜索快、试错成本低的执行工具，而 AI 恰好补上了这部分能力。因此，AI 可能让优秀工程师获得更大的产出提升；但这仍然需要真实项目数据验证，不能只根据职级下结论。

这也解释了为什么有经验的工程师更可能借 AI 获得接近 OPC（一人公司）的工程产能：他们能够决定做什么、约束怎么实现、判断结果是否合格，AI 则负责更快地写和改代码。但这只是一个条件，并不等于产品、运营与商业能力也会自动出现。

Loop Engineering 的真正价值：建立纠错，而不是重复生成

放到工程师、Agent 和代码三方关系里，Loop Engineering 的价值不是“让模型盲目再试一次”，而是每一轮都根据新结果纠正理解：

看清现状 → 做一个小改动 → 跑测试、看日志 → 比较预期和结果 → 修正理解 → 进入下一轮

测试、日志、trace、静态分析、浏览器行为和 code review，都在告诉人和 Agent“系统实际上发生了什么”。仓库地图、ADR、接口说明、决策记录和可执行示例，则把这些认识保存下来，避免下一轮从头猜。Skill 与 Harness 的价值，是帮助 Agent 在正确时机找到这些材料，并把不知道的地方暴露出来。

厂商的工程经验也在强调相似原则：从简单、可组合的模式开始，只在需要时增加 Agent 复杂度；上下文应按需检索并持续整理，而不是一次性预装全部资料。Building Effective AI Agents、Effective Context Engineering

因此，Loop Engineering 与“工程师理解系统”不是二选一。Loop 提供搜索、执行和检查结果，工程师仍要决定应该做什么、判断结果是否正确。好的 Loop 可以帮助人重新跟上代码，却不能让一个从不检查前提的人自动理解系统。

无人值守的 Agent 可以做一部分，但不能脱离条件

“自动分析需求、拆解任务、生成代码、部署上线”的 Agent 集合是否还很遥远，不能用一句“绝对不可能”回答。

对于需求清楚、影响范围明确、能够自动测试、环境隔离、出错后容易回滚的任务，高度自治已经可以工作。困难集中在需求含糊、业务规则没有写下来、改动跨越多个系统、看不到完整运行状态，以及上线风险很高的任务上。一项面向端到端软件开发的 2025 年基准研究发现，受测 Agent 系统平均只能满足约一半需求，主要失败来源是需求遗漏与自我检查不足；这是一项具体基准的结果，不能外推成所有系统的统一上限。E2EDevBench

增加 Agent 数量也不一定让结果更好。能够并行处理、分别验收的任务可能受益；必须按顺序推进、频繁共享同一份代码状态的任务，则会增加沟通成本，并把一个错误传给更多 Agent。一项 2026 年的多 Agent 系统研究展示了明显的任务差异。

比预测“还要多少年”更有用的，是建立一条授权原则：

只有当结果看得见、测得出、影响隔得开、出错退得回时，才适合给 Agent 更大的自主权。

Agent 的数量不会凭空补出缺失的业务规则。能否无人值守，也不只取决于模型有多强，还取决于任务是否清楚、仓库是否容易理解、工具是否可靠，以及测试和发布控制是否完善。

在发射 Agent 前，先建立任务同步包

给 Agent 的输入不应只有一句“实现某功能”，而应该包含一份小而完整的任务同步包：

  1. 目标与动机：要改变什么用户行为，为什么现在改变；
  2. 非目标：本次明确不解决什么，防止顺手重写；
  3. 当前事实：入口、调用链、数据所有权和已有实现；
  4. 不能破坏的规则：权限、事务、幂等、兼容、延迟和一致性要求；
  5. 架构形状与允许范围：项目采用哪一种本地模式，新组件应放在哪里，可以修改哪些模块、接口和依赖；
  6. 未知与假设：哪些仍需检索、实验或向领域专家确认；
  7. 验收标准：可执行测试、可观察信号和失败判据；
  8. 停止条件：遇到哪些冲突必须暂停，而不是继续猜；
  9. 发布与回滚：如何灰度、监控、撤销和修复数据。

Agent 开始工作后，应先查看相关代码、复述任务要求并指出冲突，再提出最小改动；每轮修改都要留下可以检查的 diff 和测试结果。任务结束后，把新发现的规则写回测试、ADR、运行手册或代码结构。同步不是写一次 prompt，而是持续让工程师、Agent 和代码保持一致。

怎么测工程师与代码仓库是否同步

这里有一个需要用真实项目验证的猜想：工程师越了解当前任务涉及的代码和系统，Agent 任务的成功率是否越高，返工和缺陷是否越少？ 可以用一个 assess-repo-sync Skill 来测试这个猜想，但第一版不应急着给工程师一个永久的“78 分”。

更准确的评估对象是：

针对一个具体任务，检查某位工程师对当前仓库版本了解到了什么程度，还缺哪些关键知识。

每次评估都必须写清楚：评估谁、哪个 commit、什么任务、允许查看哪些资料和工具，以及评估时间。脱离这些条件的分数没有意义。

它应至少区分三个结果：

  • 当前了解程度：不查资料时，对系统现状能说对多少；
  • 重新跟上代码的能力：开放仓库、文档、测试和 Agent 后，能否快速找到证据并改正错误；
  • 任务准备程度：补完缺失知识后，适合给 Agent 多大的自主范围。

评估维度也应该保持多维，而不是用平均分掩盖致命短板：

维度 需要测量的问题
需求来龙去脉 是否知道需求为什么这样定，哪些规则不能破坏？
系统实际运行路径 是否能解释请求、数据和事件实际经过哪里？
改动会影响哪里 是否能找出接口、缓存、索引和下游系统的影响？
底层技术理解 是否理解本任务涉及的事务、缓存、搜索或流处理机制？
怎么证明改对了 是否能给出可执行的验收方式、失败信号和检查位置？
怎么上线和撤回 是否知道如何灰度、回滚、修复数据和控制影响范围？
是否知道自己不知道 判断没把握时，是否会停下来找证据或请教专家？
能否把任务交代清楚 是否能写清目标、非目标、验收和停止条件？
是否理解本地架构约定 是否知道该任务遵守哪种处理形状、扩展点，以及哪些边界不能绕开？

前端直连 ES 的例子需要拆成两个问题：不知道当前仓库里的真实调用路径，说明工程师没有跟上代码；不知道 Elasticsearch 的部署、安全和访问边界，说明工程师不熟悉这项技术。两者都会影响 Agent 任务，却不是同一个原因。

评估还应把人的同步程度与仓库的可同步性分开。关键流程是否有可查看的拓扑，Processor 的输入输出是否明确，架构约定能否被测试，文档是否与当前 commit 一致，都会影响一个人重新跟上代码的成本。如果这些基础条件缺失，工具应报告“仓库难以同步”，而不是把所有知识缺口都归因于工程师。

两阶段测量，而不是背代码考试

第一阶段不允许查资料，让受测者解释运行路径、预测影响、识别风险，并说明每个判断有多大把握。第二阶段开放仓库、文档、测试和 Agent，要求引用证据并允许改答案。使用工具不是作弊：真实工作本来就需要靠工具重新跟上代码。

题目应考因果、预测、验证和纠错，而不是类名记忆，例如：

  • 这个改动的真实运行路径是什么？每一段调用关系的证据在哪里？
  • 哪些模块、协议、缓存、索引或消费者可能受影响？
  • “让前端直连 ES 可以少一跳”这个方案遗漏了什么边界？
  • 如果 MySQL 更新成功而索引延迟，用户会观察到什么？如何发现和恢复？
  • 请为 Agent 写出本任务的非目标、验收、停止条件和回滚要求。

第一版评分不必套复杂公式，只需要清楚报告四件事：关键事实答对了多少、漏掉了哪些高风险事实、每个判断有没有代码或测试证据，以及把握很大的判断是否真的正确。一个高置信度的错误技术决策，应当比诚实地说“不确定，需要先验证”受到更重的扣分。

说明 Agent 可以做到哪一步，而不是给人贴标签

Skill 最终应输出：已经了解的内容、知识缺口、判断依据，以及补齐缺口所需的文件和检查项。然后再建议 Agent 可以做到哪一步：

  • L0 — 证据不足：先补资料或专家确认；
  • L1 — 探索/规划：Agent 只检索、解释和提出方案；
  • L2 — 受控修改：允许生成补丁，关键节点人工确认；
  • L3 — 有界自主：在明确目录、测试和回滚边界内闭环实现。

生产发布权限应由独立的工程控制决定，不能因为同步评估为绿色就自动授予。这个工具也不应被用来给人贴“懒惰、平庸”的标签；高级工程师可能不了解一个新模块，初级工程师也可能与自己维护的子系统高度同步。

先验证这个评分有没有用，再用它拦任务

assess-repo-sync 的第一版应该运行在 shadow mode，也就是只给建议，不阻止 Agent 发射。

可以先收集一批真实的“工程师—任务”组合，在任务开始前完成评估，然后跟踪：

  • 首次评审通过率和严重 review comment 数；
  • 需求返工、测试遗漏和逃逸缺陷；
  • Agent 循环次数、人工接管点和回滚；
  • 完成时间，但不把速度当作主要质量指标。

比较结果时，要把职级、接触仓库的时间、任务难度、测试覆盖、文档质量、所用模型和工具分别考虑进去。真正要验证的是：这个评估是否比“职级＋熟悉时长＋任务难度”更能预测质量。

随后再做对照实验：一组沿用普通 Agent 流程，另一组先评估，再获得针对性的必读文件、待确认问题和 Agent 停止条件。只有后一组确实减少关键遗漏与返工，才能说明这个 Skill 测到的是可以补救的知识缺口，而不是另一种包装过的资历判断。

还要防止工程师为了分数背题，而不是真正理解系统；也要防止 LLM 自己出题、自己评分，或者拿过期文档当标准答案。每次结果必须绑定 task + commit + timestamp，并设置有效期。仓库本身缺少可靠资料时，应报告“仓库知识不足”，而不是把责任全部扣到工程师身上。评估结果也不应直接用于绩效排名。

结语：代码可以交给 AI，理解不能缺席

Loop Engineering 仍然具有明确价值，Agent 也正在承担越来越长的任务。需要警惕的不是 AI 太强，而是人在实现动作被自动化以后，可能没有察觉自己的系统理解也在逐渐退化。

工具能减少手写代码、搜索 API 和机械调试的成本，却不会自动生成正确的业务目标、架构边界和责任判断。优秀工程师得到的不是一位替他思考的神，而是一套能够快速写代码、查资料和跑实验的工具。

所以，AI 编程不是从 prompt 直接通向代码的一条直线。工程师、Agent 和最终交付的代码必须持续对上；测试和运行结果一旦暴露偏差，就要及时修正。Loop Engineering 的下一步，不只是让 Agent 跑得更久、Skill 更多、编排更复杂，还要让工程师知道自己何时没跟上代码，以及怎样重新跟上。

AI 可以替你敲下代码，但不能让你自动理解一个自己从未认真了解过的系统。
